Video+/Audio+ 앱 파티션 저장소: 구조, 최대 용량, 로그아웃 삭제

Video+(picknowweb)와 Audio+(pickaudioweb)가 쓰는 앱별 StoragePartition의 구조, 이 단말 기준 최대 용량, 실제 사용에서 예상되는 크기, 로그아웃 때 지우는 범위와 단말 스트레스 테스트 결과를 정리했습니다.

요약

  • 앱마다 저장소가 따로입니다. 쿠키, 캐시, IndexedDB 등 CP 데이터는 Storage/ext/<appId>/def에 앱별로 쌓입니다. 방문 기록, 설정 같은 프로필 공용 데이터와는 분리돼 있습니다.
  • 이 단말 기준 이론상 최대는 앱 하나에 약 5.9GB로, 디스크 전체(약 5.8GB)보다 큽니다. 그래서 실제 한계는 디스크 여유 공간(빈 단말 약 5.2GB)입니다.
  • 실제 사용에서 예상되는 최대는 앱 하나에 약 1~1.3GB입니다. HTTP 캐시(800MB)와 Code 캐시(200MB)는 오래 쓰면 상한까지 차지만, 쿠키와 저장소는 사이트 수가 적어 상한에 가지 않습니다.
  • 로그아웃하면 Home origin만 남기고 그 앱의 CP 데이터를 지웁니다. 단말에서 Video+ 216MB가 36MB로, 쿠키 380개가 1개(Home)로 줄었고 약 1.7초 걸렸습니다.

1. 컨셉

  • 파티션 분리: OBIGO_APP_STORAGE_PARTITION이 켜져 있으면 GetStoragePartitionConfigForSite()가 appId를 파티션 이름으로 씁니다. 같은 CP(예: YouTube)를 두 앱에서 열어도 쿠키와 캐시가 따로 저장됩니다.
  • 로그인이 따로입니다. 두 앱은 Home 로그인도 따로입니다. 토큰은 Home origin의 Local Storage(picknow-access-token, pickaudio-access-token)에 있고, JWT라 sid가 들어 있으며 24시간 유효합니다. 앱을 띄울 때마다 새로 발급받습니다.
  • 로그아웃 감지: Home이 obaJs.storeAccessToken으로 토큰을 브라우저에 알려줍니다. 브라우저는 앱별 토큰 맵을 두고 "이 앱의 토큰이 있다가 비었을 때"를 로그아웃으로 판단합니다.
    • 로그인된 Home은 앱을 띄울 때마다 토큰을 한 번 보냅니다.
    • 게스트 Home은 호출하지 않습니다.
    • 로그아웃하면 빈 토큰을 두 번 보냅니다(계정 페이지에서 한 번, 다시 로딩된 Home에서 한 번).
  • 삭제 범위: 로그아웃한 앱의 파티션만 지웁니다. Home origin(https://stg-picknow.obigo.ai)의 데이터와 쿠키는 남겨서 Home이 정상으로 다시 뜨게 합니다. 다른 앱 파티션과 프로필 공용 파일은 건드리지 않습니다.
Home 로그아웃 버튼 → obaJs.storeAccessToken("") (renderer) → ObaJsImpl::StoreAccessToken (browser UI, app_id 확인) → BookMarkClient::storeAccessToken (extension: prev 토큰 있음 && 새 토큰 빈 값 → 로그아웃) → WebAppExtensionDelegateImpl::ClearAppStorageData → obigo::ClearAppStorageData(profile, app_id, home_url) StoragePartition::ClearData (Home origin 제외) 쿠키: Home host 쿠키만 남기고 삭제 HTTP 캐시: Home origin 제외 / Code 캐시: 전체 NetworkContext: HSTS·네트워크 기록, HTTP auth, Reporting/NEL, CORS preflight, Trust Token, Shared Dictionary

3. 이 단말 기준 최대 용량 (Chromium 143 코드 기준)

단말 /ccos/data는 전체 5977MiB(약 5.8GB)입니다. 다른 데이터가 약 0.7GB를 써서, 앱 데이터가 없을 때 여유 공간은 약 5.2GB입니다. Chromium은 저장소와 캐시 상한을 이 디스크 크기에서 계산하고, obigo 전용 상한은 없습니다.

  • 설정의 "인터넷 사용 기록 삭제 → 캐시된 이미지 및 파일"은 현재 앱 파티션의 HTTP 캐시만 보여줍니다(cache_counter.cc obigo 수정). Code 캐시는 포함되지 않습니다. 디스크 사용량(du)보다 조금 작게 나오는데, blockfile이 미리 잡아두는 data_N 파일과 index 때문입니다(예: 화면 366MB, du 395MB).

6. 스트레스 테스트

  1. 로그인 백업
    두 앱이 로그인된 상태를 백업하고 복원이 되는지 확인했습니다.

    서비스를 멈추고 두 앱 파티션을 tar로 묶었습니다. Video+를 로그아웃한 뒤 복원하니 다시 로그인 상태로 떴습니다. 서버가 로그아웃 때 세션을 끊지 않아서, 같은 로그인 상태로 반복 테스트할 수 있습니다.

  2. 채우기
    Video+ CP 21~22곳을 CDP로 돌며 데이터를 쌓았습니다.

    CP마다 페이지 열기 → 스크롤 → 같은 사이트 링크 3개 이동 → 영상 15초 재생 순서로 돌았습니다. 여기에 쿠키 40개, Local Storage, IndexedDB 4MB, CacheStorage 2.5MB, force-cache fetch를 강제로 더했습니다.

  3. 1GB
    1038MB에서 멈췄습니다.

    HTTP 캐시 395M, IndexedDB 234M, Service Worker 223M, Code 캐시 179M, 쿠키 2797개였습니다. 서비스 재시작은 없었습니다. 이 상태는 PC에 백업했습니다(아래).

  4. 1.24GB
    1244MB에서 채우기를 멈추고 백업했습니다.

    HTTP 캐시 414M, IndexedDB 340M, Service Worker 288M, Code 캐시 192M, 쿠키 약 2900개였습니다. HTTP 캐시는 같은 CP를 다시 돌면 새로 쌓이는 게 거의 없어서 상한(800MB)까지 가지 않았습니다.

  5. 로그아웃
    Video+를 직접 로그아웃했고 결과는 정상입니다.

    14:31:50에 삭제를 시작해 14:31:56에 HTTP 캐시까지 끝났습니다(약 5.6초). 쿠키 2916개를 지우고 Home 쿠키 1개만 남겼고, 파티션은 1244M에서 102M이 됐습니다. 남은 HTTP 캐시 100M은 blockfile data_N 파일 크기가 줄지 않은 것입니다. 두 번째 빈 토큰은 changed: 0이라 다시 삭제하지 않았습니다. Home은 에러 없이 다시 로딩됐고, 크래시와 재시작은 없었습니다. 로그아웃 직전의 서비스 재시작은 수동 stop/start였습니다.

7. 함께 정리한 코드 변경 (브랜치 dev_roya_HKMCCCNCMO-5807_01)

  • 방문 기록 저장 끄기: profile_impl.cc에서 OBIGO_WEB_SOLUTION일 때 prefs::kSavingBrowserHistoryDisabled를 true로 둡니다. obigo는 History를 읽지 않는데 CP URL이 쌓였습니다.
  • 보류한 공용 데이터: Sessions(1.3MB, CP URL 포함), Favicons, 로딩 예측, DIPS입니다. 모두 수 MB 이하이고 Chromium이 크기를 스스로 관리합니다. 개인정보 요구가 생기면 Sessions만 다시 봅니다.
  • 사용자 행동·사용시간 로그의 토큰: 토큰을 앱별 맵으로 바꾸면서 getAccessToken(cur_app_id_)가 백그라운드 재생 일시정지, 전원 끔, 사용자 전환 때 빈 토큰을 보내는 회귀가 생겼습니다. 마지막으로 띄운 PickNow 앱(last_picknow_app_id_)의 토큰을 쓰도록 고쳤습니다(작업 트리, 커밋 전).
  • 로그: storeAccessToken 경로에 INFO 로그를 남깁니다. 토큰 값은 남기지 않고 길이와 해시만 남깁니다.
