CCOS sig handler를 유지하면서 webappmanager에서도 crash stack trace 받기

크래시 시그널을 되찾아 백트레이스를 찍고 원래 주인에게 넘겨주는 체이닝 구현 리뷰입니다. 두 SDK의 바이너리를 역어셈블한 결과, MOBIS_CCNC와 MOTREX_CCNC는 시그널을 잡는 주체도, 그 핸들러의 종료 방식도 완전히 다릅니다. 하나의 #if로 묶여 있지만 답은 플랫폼마다 갈립니다.

01 결론

"둘 다 동작 가능한가"에 대한 답은 플랫폼마다 다릅니다.

MOTREX_CCNC — 가능

상대는 libdlt 2.17.0의 dlt_sig_handler입니다. 이 핸들러는 플랫폼 리포트를 보낸 뒤 raise()하고 return 합니다. 따라서 체이닝 후에도 우리 코드로 제어가 돌아오고, 양쪽 모두 정상 동작합니다.

다만 sysroot 전체에서 dlt_signal_handler_registration()을 호출하는 라이브러리가 하나도 없습니다. 실제로는 애초에 경쟁자가 없었고, DLT에 백트레이스가 안 남던 진짜 원인은 핸들러 진입 즉시 FinalizeLogger()가 DLT를 꺼버린 것일 가능성이 높습니다(#B2 참조). 이 패치의 실질적 수정은 체이닝이 아니라 FinalizeLogger() 제거 + MirrorToDlt이고, 체이닝은 보험입니다.

MOBIS_CCNC — 조건부 가능, 단 순서를 바꾸면 안 됨

상대는 libdlt가 아니라 CCOS 플랫폼의 ccos::util::trace::HDebugHandler(libhtrace.so.2.2.17)입니다. 이 핸들러는 리포트 전송 후 정상 경로에서 exit(0)을 호출하고 return 하지 않습니다.

따라서 백트레이스를 먼저 찍고 나중에 체이닝하는 현재 순서가 MOBIS에서는 유일하게 맞습니다. 체이닝을 앞으로 옮기면 MOBIS에서는 백트레이스를 통째로 잃습니다. 추가로 SA_ONSTACK 유실(#M4)과 미커버 시그널 3개(#m8)라는 별도 회귀가 있습니다.

공통 전제
  • 양쪽 모두 상대는 이전 핸들러를 체이닝하지 않습니다. 구조가 "나중에 설치한 쪽이 이긴다"이므로 이 패치의 접근이 유일한 해법인 건 맞습니다.
  • EnableInProcessStackDumping()이 상대 등록보다 반드시 나중에 호출될 것
  • 백트레이스 출력 도중 행/데드락이 안 날 것 — 현재 코드는 여기가 깨집니다 (#M5)

하나의 #if로 묶었지만 두 플랫폼의 구조가 다릅니다

05 심각

M3Major 공통 · 플랫폼별 결론 다름

체이닝 순서 — 워치독이 없습니다

alarm(5) 워치독은 체이닝보다 한참 뒤에서야 설정됩니다. 백트레이스나 DLT 미러링 중 행이 나면 아무도 못 깨우고, 플랫폼 크래시 리포트까지 같이 유실됩니다.

조치 공통 — alarm() + SIGALRM 핸들러 설치를 in_signal_handler = 1; 직후로 앞당깁니다. 무슨 일이 있어도 5초 안에 exit_group 보장. 이게 가장 비용 대비 효과가 큽니다.

MOTREX ChainToPreviousHandler()를 백트레이스 앞으로 옮겨도 됩니다. dlt_sig_handler는 return 하므로 백트레이스는 그대로 찍히고, 플랫폼 리포트가 먼저 나가 안전합니다.

MOBIS 옮기면 안 됩니다. HDebugHandler는 exit(0)으로 끝나므로 체이닝을 앞에 두면 백트레이스를 통째로 잃습니다. 현재 순서를 유지하세요.
src/base/debug/stack_trace_posix.cc:565-576, 647-654
M4Major MOBIS

SA_ONSTACK 유실 — 스택 오버플로 크래시를 못 잡게 됩니다

HDebugHandler는 sa_flags = SA_ONSTACK | SA_RESTART | SA_SIGINFO로 등록합니다. 대체 시그널 스택에서 동작하므로 스택 오버플로로 인한 SIGSEGV도 처리할 수 있었습니다.

그런데 Chromium의 EnableInProcessStackDumping()은 SA_RESETHAND | SA_SIGINFO만 쓰고 SA_ONSTACK이 없습니다. 시그널을 뺏은 뒤에는 오버플로된 스택 위에서 핸들러가 돌다 즉시 이중 폴트 → SIG_DFL 강제 종료. 백트레이스도, 플랫폼 리포트도 둘 다 유실됩니다. 기존보다 확실히 나빠지는 지점입니다.

조치MOBIS에서 이 스위치를 켤 거면 sigaltstack() 설정 + action.sa_flags |= SA_ONSTACK를 같이 넣거나, 최소한 알려진 제약으로 문서화
src/base/debug/stack_trace_posix.cc:1091-1093
M5Major 공통

시그널 핸들러 안의 WriteLog() — 데드락 가능

WriteLog → ImplHLogDelegate::WriteLog → WebAppLog::printLog(std::shared_ptr<DltContext>, ...). 시그니처상 shared_ptr 복사(refcount) + 내부 DLT 세마포어가 들어갑니다. 크래시가 로깅 경로 안에서(또는 DLT 락 보유 중) 발생하면 같은 스레드가 자기 락을 기다리며 영구 행입니다. 양쪽 플랫폼 모두 PAL을 경유하므로 동일하게 해당됩니다.

EnableInProcessStackDumping()의 워밍업은 컨텍스트 지연 등록만 막습니다. 호출당 락/할당은 못 막습니다. 기존 코드가 핸들러 맨 앞에서 FinalizeLogger()를 부르던 게 정확히 이 위험 회피였을 수 있다는 점도 고려해 주세요.

조치M3의 alarm() 선행 이동이 실질적 안전장치입니다. 더 안전하게 가려면 기동 시 미리 열어둔 fd에 write()만 하는 fallback 경로를 두는 방법도 있습니다.
M6Major 공통

MirrorToDlt가 스위치와 무관하게 항상 동작합니다

PrintToStderr()의 가드는 OBIGO_USE_LOG_SYSTEM && ARCH_CPU_ARM64뿐이고 kEnableCrashStackTrace와 무관합니다. 스위치가 off여도 DCHECK 실패, DumpWithoutCrashing(), 각종 StackTrace().Print() 출력이 전부 DLT로 나갑니다.

여기에 더해 is_official_build = false라서 content_main_runner_impl.cc:996-999가 이미 모든 프로세스에서 EnableInProcessStackDumping()을 호출하고 있습니다. 즉 이 스위치가 실제로 제어하는 건 "스택 덤프 활성화"가 아니라 "상대에게서 시그널을 되찾아오기"입니다. 스위치 이름·주석과 실제 의미가 어긋납니다.

조치전역 bool g_mirror_to_dlt = false;를 두고 EnableInProcessStackDumping()에서 스위치 값으로 세팅, MirrorToDlt() 진입부에서 early return

06 중간

m7MediumMOBIS

exit(0) 때문에 정리 코드가 실행되지 않고, 크래시가 정상 종료로 보입니다

  • FinalizeLogger()가 실행되지 않음 — DLT 애플리케이션이 등록된 채로 프로세스 종료
  • [end of stack trace]가 출력되지 않음 — 로그 완결 여부 판별 불가
  • 종료 코드 0 — systemd / CCOS 앱매니저가 크래시를 정상 종료로 오인할 수 있음
  • _exit가 아니라 exit이므로 손상된 프로세스에서 atexit 핸들러와 static destructor가 실행됩니다. Chromium은 static dtor가 많아 2차 크래시/행 위험
  • 코어 덤프 없음

플랫폼 동작이라 우리가 못 바꾸지만, MOBIS에서는 이게 정상 결과라는 걸 알고 로그를 읽어야 합니다.

m8MediumMOBIS

커버되지 않는 시그널 3개

HDebugHandler는 8개를 잡지만 base는 5개만 가져옵니다 (Linux에서 SIGSYS는 seccomp 때문에 의도적으로 제외). SIGTRAP(5) · SIGSTKFLT(16) · SIGSYS(31)은 여전히 HDebugHandler가 소유하므로 webappmanager 백트레이스가 남지 않습니다. 패치의 g_previous_handlers 캡처 루프도 5개만 돕니다.

의도한 범위라면 문제없지만, "SIGTRAP 크래시인데 왜 로그가 없지?"를 나중에 다시 조사하지 않도록 명시가 필요합니다.

m9MediumMOTREX

FinalizeLogger() 위치 때문에 [end of stack trace]가 DLT에 안 남습니다

StackTrace().Print()  →  FlushDltLine()  →  Chain  →  FinalizeLogger()
   →  (x86 전용 레지스터 덤프, ARM64에선 skip)
   →  PrintToStderr("[end of stack trace]\n")   ← WriteLog는 이미 early return

종료 마커가 없으면 로그가 잘린 건지 정상 종료한 건지 구분이 안 됩니다.

조치FinalizeLogger()를 "[end of stack trace]" 출력 + FlushDltLine() 뒤, re-raise 직전으로 이동. (MOBIS는 m7 때문에 어차피 도달하지 않습니다)
m10Medium공통

g_dlt_line 전역 버퍼에 동기화가 없습니다

PrintToStderr()는 시그널 컨텍스트 밖에서도 쓰입니다(임의 스레드의 StackTrace().Print()). 락이 없어 두 스레드 출력이 한 줄로 섞이고, 크래시 첫 줄의 [WMP][##CRASH##] 프리픽스가 누락될 수 있습니다.

경계는 확인해 봤고 오버플로는 나지 않습니다. 다만 프리픽스 복사 루프에는 경계 검사가 아예 없습니다 — 지금은 17바이트라 안전하지만 kDltCrashPrefix가 길어지면 바로 깨집니다.

m11Medium공통

512바이트 라인 잘림

C++ 심볼(템플릿 · 람다 · Blink 네임스페이스)은 512자를 쉽게 넘습니다. DLT 자체 한계는 1390(0x56e, libdlt 내부 상수로 확인)이므로 1024 정도로 올리는 걸 권장합니다.

08 크래시 없이 검증하는 방법

두 플랫폼 모두 "상대가 실제로 누구인지"가 코드만으로는 확정되지 않습니다. 아래 두 가지로 크래시 없이 판별 가능하고, 둘 다 시그널 컨텍스트 밖이라 async-signal safety 제약이 없습니다.

A. 무엇을 뺏어왔는지 확인

EnableInProcessStackDumping()의 캡처 루프 안에서:

Dl_info dli;
const void* prev = (previous.sa_flags & SA_SIGINFO)
    ? reinterpret_cast<void*>(previous.sa_sigaction)
    : reinterpret_cast<void*>(previous.sa_handler);
LOG(ERROR) << "[RLOG] sig=" << crash_signal << " prev=" << prev
           << " onstack=" << ((previous.sa_flags & SA_ONSTACK) != 0)
           << " name=" << (prev && dladdr(prev, &dli) && dli.dli_sname
                           ? dli.dli_sname : "(none/SIG_DFL)");
찍히는 값의미
debugHandlerMOBIS HDebugHandler가 소유 중 — 체이닝 유효, exit(0) 전제 확정
dlt_sig_handlerMOTREX libdlt가 소유 중 — 체이닝 유효, return 전제 확정
(none/SIG_DFL)애초에 경쟁자가 없었음 — 체이닝은 no-op, 실질 수정은 FinalizeLogger() 제거 쪽

프로세스마다 다르게 나오므로 browser / renderer / gpu / utility 4개 모두 확인

B. 나중에 다시 뺏기는지 확인

기동 후 10초 / 60초 타이머에서:

struct sigaction cur = {};
sigaction(SIGSEGV, nullptr, &cur);
LOG(ERROR) << "[RLOG] SIGSEGV owner still ours? "
           << (cur.sa_sigaction == &StackDumpSignalHandler);

CCOS/PAL이 lazy하게 나중에 등록하는 구조라면 false가 찍히고, 그 경우 EnableInProcessStackDumping() 호출 지점을 더 뒤로 옮겨야 한다는 결론이 바로 나옵니다. A의 onstack 값은 M4(SA_ONSTACK 유실) 확인용입니다.
