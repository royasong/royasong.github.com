크래시 백트레이스를 DLT로 내보내고, 시그널을 원래 주인에게 되돌려 플랫폼 크래시 리포트를 유지하는 구현입니다. 두 SDK 바이너리를 역어셈블한 결과 MOBIS_CCNC와 MOTREX_CCNC는 시그널을 잡는 주체도, 그 핸들러의 종료 방식도 완전히 다릅니다. 이 문서는 그 분석과 최종 코드 상태를 담습니다.

01 결론

체이닝은 이 플랫폼에서 성립하는 유일한 해법이 맞습니다. 다만 실제로 문제를 풀어준 건 체이닝이 아니었습니다.

둘 다 동작 가능

MOBIS의 HDebugHandler도, MOTREX의 dlt_sig_handler도 sigaction()에 이전 핸들러를 저장하지 않습니다. 구조가 "나중에 설치한 쪽이 무조건 이긴다"이므로, 나중에 설치하고 이전 핸들러를 직접 호출해 주는 이 방식이 유일하게 성립 가능한 해법입니다.

dlt_sig_handler는 raise() 후 return하므로 체이닝 뒤에도 제어가 돌아옵니다. HDebugHandler는 exit(0)으로 끝나 돌아오지 않지만, 백트레이스를 먼저 찍고 체이닝하므로 양쪽 모두 백트레이스와 플랫폼 리포트를 다 얻습니다.

단, 진짜 원인은 따로 있었습니다

sysroot 전체에서 dlt_signal_handler_registration()을 호출하는 라이브러리가 하나도 없습니다. MOTREX에서는 애초에 경쟁자가 없었고, is_official_build = false라 base 핸들러는 이미 설치돼 있었습니다. 그런데도 DLT에 백트레이스가 안 남던 건 핸들러 진입 즉시 FinalizeLogger()가 DLT를 꺼버렸기 때문입니다. 그 2줄이 패치 전 이 파일의 유일한 OBIGO 개조였습니다. 실질 수정은 FinalizeLogger() 이동 + MirrorToDlt()이고, 체이닝은 보험입니다.

07 남은 제약

01Major공통

시그널 핸들러 안의 WriteLog()는 async-signal-safe하지 않습니다

WriteLog → ImplHLogDelegate::WriteLog → WebAppLog::printLog(std::shared_ptr<DltContext>, ...). shared_ptr 복사(refcount)와 내부 DLT 세마포어가 들어갑니다. 크래시가 로깅 경로 안에서(또는 DLT 락 보유 중) 발생하면 같은 스레드가 자기 락을 기다립니다.

완화됨 — 진입 시 alarm(5)로 5초 뒤 exit_group(). 행은 막지만 백트레이스는 잘릴 수 있습니다.

02Medium공통

스위치가 off여도 DLT 미러링과 체이닝은 동작합니다

content_main_runner_impl.cc:996이 #if !defined(OFFICIAL_BUILD) 안에서 스위치와 무관하게 EnableInProcessStackDumping()을 호출합니다. 이 빌드는 is_official_build = false라 항상 실행됩니다.

따라서 스위치는 릴리스(OFFICIAL_BUILD) 빌드에서만 실질적인 의미가 있습니다. DLT 포팅 관점에서는 "항상 찍힌다"가 맞는 동작이라 이대로 두었습니다.

03MediumMOBIS

커버되지 않는 시그널 3개

HDebugHandler는 8개를 잡지만 업스트림 base는 5개만 가져옵니다. SIGTRAP(5) · SIGSTKFLT(16) · SIGSYS(31)은 여전히 HDebugHandler가 소유하므로 webappmanager 백트레이스가 남지 않습니다. SIGSYS는 seccomp-bpf가 소유하므로 가져가면 안 됩니다(샌드박스 파손).

SIGTRAP 확장을 검토했으나 업스트림 동일성을 택해 제외했습니다 — 09장 참조.

04MediumMOBIS

스택 오버플로 크래시는 잡히지 않습니다

업스트림 EnableInProcessStackDumping()은 SA_ONSTACK을 쓰지 않으므로, 고갈된 스택 위에서 핸들러가 돌다 이중 폴트합니다. HDebugHandler는 SA_ONSTACK을 걸지만 sigaltstack()을 호출하지 않아 실제로는 무효입니다(sysroot 심볼 확인). 따라서 기존 대비 회귀는 아닙니다.

sigaltstack() 도입을 검토했으나 업스트림 동일성을 위해 제외했습니다. 필요하면 스레드별 설치가 필요합니다.

05MediumMOTREX

체이닝 대상이 실제로 존재하는지 미확인

dlt_signal_handler_registration()을 호출하는 라이브러리가 sysroot에 없습니다. 경쟁자가 없으면 ChainToPreviousHandler()는 no-op이 되고 해는 없지만, 전제가 확정되지 않은 상태입니다. 08장의 진단 로그로 확인 가능합니다.

06Low공통

g_dlt_line 전역 버퍼에 동기화가 없습니다

PrintToStderr()는 시그널 컨텍스트 밖에서도 쓰입니다(다른 스레드의 StackTrace().Print()). 락이 없어 출력이 섞이거나 [WMP][##CRASH##] 프리픽스가 누락될 수 있습니다. 오버플로는 나지 않음을 확인했습니다.

07LowMOTREX

motrex-ccnc는 release config 분기가 없습니다

빌드 스크립트가 motrex에 대해서는 configuration/motrex-ccnc/를 그대로 복사합니다 (mobis만 release/ 분기 존재). 지금 on으로 둔 값이 양산에도 그대로 나갑니다.

08 크래시 없이 검증하는 방법

"상대가 실제로 누구인지"는 코드만으로 확정되지 않습니다. 아래 두 가지는 시그널 컨텍스트 밖이라 안전합니다.

A. 무엇을 뺏어왔는지

// EnableInProcessStackDumping() 의 캡처 루프 안
Dl_info dli;
LOG(ERROR) << "[RLOG] sig=" << crash_signal << " prev=" << previous_handler
           << " name=" << (previous_handler && dladdr(previous_handler, &dli)
                           && dli.dli_sname ? dli.dli_sname : "(none/SIG_DFL)");
찍히는 값의미
debugHandlerMOBIS 체이닝 유효 · exit(0) 전제 확정
dlt_sig_handlerMOTREX 체이닝 유효 · return 전제 확정
(none/SIG_DFL)경쟁자 없음 — 체이닝은 no-op, 실질 수정은 FinalizeLogger() 쪽

프로세스마다 다르므로 browser / renderer / gpu / utility 4개 모두 확인

B. 나중에 다시 뺏기는지

// 기동 후 10초 / 60초 타이머
struct sigaction cur = {};
sigaction(SIGSEGV, nullptr, &cur);
LOG(ERROR) << "[RLOG] SIGSEGV owner still ours? "
           << (cur.sa_sigaction == &StackDumpSignalHandler);

false가 찍히면 CCOS/PAL이 lazy하게 나중에 등록한다는 뜻이고, EnableInProcessStackDumping() 호출 지점을 더 뒤로 옮겨야 한다는 결론이 나옵니다.

09 초기 분석 정정

이 문서의 이전 판에 있던 두 가지 오류입니다.

정정 1Corrected

"arm64에서 CHECK 크래시는 백트레이스가 없다"는 틀렸습니다

arm64의 IMMEDIATE_CRASH()가 brk #0(SIGTRAP)인 것은 맞습니다 (immediate_crash.h:91). 그러나 logging.cc:724-728이 LOGGING_FATAL 경로에서 이미 백트레이스를 찍고, 그 결과가 logging.cc:808의 WriteLog()로 DLT에 나갑니다. 

#if !defined(OFFICIAL_BUILD) && !defined(__UCLIBC__) && !BUILDFLAG(IS_AIX)
  if (severity_ == LOGGING_FATAL && !base::debug::BeingDebugged()) {
    base::debug::StackTrace stack_trace;
    stream_ << std::endl;
    stack_trace.OutputToStream(&stream_);

CHECK() / NOTREACHED() / LOG(FATAL)은 원래도 커버됐습니다. 시그널 컨텍스트가 아니라 완전 심볼라이즈된다는 점에서 오히려 낫습니다. SIGTRAP이 메우는 건 로깅을 우회하는 base::ImmediateCrash() 직접 호출 등 좁은 범위라 업스트림 동일성을 택해 제외했습니다.

단, 저 블록은 #if !defined(OFFICIAL_BUILD)입니다. 릴리스 빌드에서는 FATAL 백트레이스가 빠지고, 크래시 리포트는 플랫폼 핸들러 몫이 됩니다.

정정 2Corrected

"symbol_level = 0이면 주소만 나온다"는 과했습니다

symbol_level은 DWARF 디버그 정보(-g)만 제어합니다 (compiler/BUILD.gn:3308 → -g0). 함수명이 나오는 ELF .symtab과는 무관하고, 스트립(-Wl,--strip-debug)은 is_android일 때만 붙으므로 Linux 타깃에는 심볼 테이블이 남습니다.

설정함수명파일:줄비용
symbol_level = 0 (현재)나옴안 나옴—
symbol_level = 1나옴나옴바이너리·링크시간 증가
symbol_level = 2나옴나옴백트레이스 목적엔 불필요

줄번호는 logging.gni:17의 enable_stack_trace_line_numbers = symbol_level > 0에 달려 있습니다. 실기기 테스트에서 함수명이 정상 출력됨을 확인했으므로 양산은 0 유지가 맞습니다. 줄번호가 필요하면 같은 리비전 바이너리에 addr2line으로 복원하면 됩니다. 

aarch64-linux-gnu-addr2line -f -C -e w20 0x1234abc
