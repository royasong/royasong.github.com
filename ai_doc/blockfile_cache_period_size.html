Blockfile 캐시 기간별 용량 표시

설정 > 인터넷 사용 기록 삭제의 "캐시된 이미지 및 파일" 용량이 기간을 바꿔도 항상 전체 크기로 표시되던 문제를, 원본 Chromium 143(PC 검증 환경)에서 수정하고 mobis CCNC(brs_143)로 옮겨 단말에서 확인한 내용을 정리했습니다.

요약

원인: blockfile 백엔드에 기간별 크기 계산(CalculateSizeOfEntriesBetween)이 없어 ERR_NOT_IMPLEMENTED를 돌려주고, HttpCacheDataCounter가 전체 크기(CalculateSizeOfAllEntries)로 대체하면서 상한 문구("Less than xx MB")를 표시했습니다.

최종 구현 (B안): 기간 안에 사용된 엔트리의 key + 데이터 크기 합을 계산합니다. 엔트리 선택은 원본 기간 삭제(SyncDoomEntriesBetween)와 같은 순회를 씁니다. 삭제 코드는 바꾸지 않았습니다.

상태: 원본 143에 반영했고, 빌드와 net_unittests 관련 테스트 22개를 통과했습니다. CCNC(brs_143)로 옮겨 단말(Video+)에서 확인했습니다. 설정 화면 값이 오프라인 계산값과 일치하고, 캐시를 상한 가까이(21,317개, 787 MB) 채운 상태에서도 "계산 중"은 2~3초입니다.

캐시 상한: 단말 Video+ HTTP 캐시 상한은 남은 공간으로 계산한 800 MiB이고, 어느 단말이든 최대 1280 MiB입니다.

최종 요구 조건

조건내용결과
1삭제 루틴은 원본 Chromium blockfile 삭제와 동일하게 유지 (관련 루틴 코드 변경 없음)충족
2기간별 삭제 시 확보 용량 표시를 기간마다 다르게 계산충족
3표시값 = 삭제 후 du 감소량요청에 따라 제외
4Cache_Data 폴더(HTTP 캐시) 기준으로 기간별 삭제 용량 계산충족

요청 사항과 결정 흐름

  1. 요청 1

    기간별로 용량이 재계산되도록 수정

    blockfile에 CalculateSizeOfEntriesBetween 추가 (key + 데이터 합).

  2. 리뷰 반영

    종료 시각 null 처리, 단위 테스트

    null 종료 시각은 상한 없음으로 처리하고, 순서가 뒤집힌 범위는 0으로 처리. 매크로 조건에 맞춰 기존 테스트를 조정하고 새 테스트 추가.

  3. 요청 2

    표시를 실제 반환 디스크 용량(du) 기준으로

    A안 개발: f_ 파일 할당 블록, sparse 자식, 확장 블록 파일, 전체 기간 RestartCache/TrimCache 모사.

  4. PC 검증

    원본 143 반영, 로그와 검증 스크립트

    [RLOG]와 cache_period_size.py로 값 일치 확인. faketime 데이터에서 1시간 = 24시간이 되는 현상을 원본 순회의 조기 종료(rankings 순서 ≠ 시각 순서)로 규명하고, 스크립트에 "Chrome 순회 기준" 표를 추가.

  5. 요청 3

    Code Cache, Shared Dictionary 합산

    구현했지만 수정 범위(13개 파일, 약 470줄)가 커서 전부 원복. 두 데이터는 같은 삭제로 기간만큼 지워지지만 표시값에서는 제외하기로 결정.

  6. 요청 4

    du 일치 조건 제외 → B안으로 단순화

    성능과 코드 양을 이유로 논리 크기 합(B안)을 선택. 전체 기간은 원본 그대로 num_bytes.

  7. 리뷰 반영

    sparse 자식 누락 수정

    기간 안 sparse 부모를 지우면 원본 삭제(DeleteEntryData() → SparseControl::DeleteChildren())가 자식도 시간과 무관하게 함께 지우는데, B안 계산에서 자식이 빠지던 문제. 부모의 자식 맵으로 자식을 찾아 함께 합산하도록 수정.

  8. 리뷰 반영

    안정성과 정확도 보강

    손상 엔트리의 음수 크기는 0으로 처리해, 설정 화면이 "계산 중"에 멈추는 경로를 막음. 순회 뒤 iterator를 항상 정리하고, 자식은 key 목록 없이 하나씩 조회하도록 바꿈. NewEviction 모드에서 evict된 자식(ENTRY_EVICTED)은 원본 삭제가 지우지 않으므로 합산에서 제외. sparse 테스트는 비동기 자식 삭제를 기다리도록 했고, 일반(V1) eviction에서는 열기만 해서는 순위가 갱신되지 않아 부모 stream 0에 쓰는 방식으로 수정.

최종 구현 (B안)

설정 화면에서 기간 선택 → CacheCounter::Count() (chrome, UI 스레드) → NetworkContext::ComputeHttpCacheSize() (network 서비스) → HttpCacheDataCounter ├ 전체 기간 : CalculateSizeOfAllEntries() → index 헤더 num_bytes (원본 그대로) └ 기간 지정 : CalculateSizeOfEntriesBetween() → InFlightBackendIO OP_SIZE_BETWEEN (캐시 스레드) → BackendImpl::SyncCalculateSizeOfEntriesBetween() ← 추가 → bytes → 화면 문구 "Frees up xx MB" (1 MB 미만이면 "Less than 1 MB")
  • 원본 SyncDoomEntriesBetween()과 같은 순회(OpenNextEntryImpl)로 최근 엔트리부터 꺼내고, 기간 시작보다 오래된 엔트리를 처음 만나면 멈춥니다. 그래서 세는 엔트리와 실제로 지워지는 엔트리가 같습니다.
  • 엔트리마다 key_len + data_size[0..2]를 더합니다. 이미 읽은 엔트리 헤더 값만 씁니다.
  • sparse 부모(미디어 range 캐시)는 원본 ChildrenDeleter와 같은 방식으로 자식을 찾아 함께 셉니다. 디스크의 자식 맵(stream 2)을 읽고, 자식 key(Range_<부모 key>:<signature>:<id>)로 MatchEntry 조회합니다. 부모를 읽기용으로 열지 않으므로 순위는 바뀌지 않고, 순회에서 다시 만나는 자식은 중복으로 세지 않습니다.
  • 찾은 자식 중 state가 ENTRY_NORMAL인 것만 셉니다. 원본 ChildrenDeleter는 SyncDoomEntry() → OpenEntryImpl() 경로로 자식을 지우는데, 이 경로는 evict된 엔트리(NewEviction 모드의 ENTRY_EVICTED, 데이터는 없고 key만 남음)를 버리기 때문입니다. 순회로 꺼내는 엔트리는 원본 순회가 정상 목록(0~2)만 돌므로 따로 거르지 않습니다.
  • 크기 값이 음수인 손상 엔트리는 0으로 셉니다. NewEntry()는 DataSanityCheck()가 실패해도 FixForDelete()로 주소만 정리하고 크기 값은 그대로 둡니다. 합계가 음수가 되면 CacheCounter가 에러로 보고 결과를 보고하지 않아, 화면이 "계산 중"에 멈추기 때문입니다.
  • 종료 시각이 null이면 상한 없음, 순서가 뒤집힌 범위는 0입니다.
  • 정확한 값이므로 is_upper_limit가 false가 되어, 상한 문구 대신 정확한 문구가 나옵니다.

성능

  • 계산은 설정 화면을 열거나 기간을 바꿀 때만, 캐시 스레드에서 돕니다. UI는 멈추지 않습니다.
  • 순회 실행 시점이 늘었습니다. 전에는 사용자가 실제로 삭제할 때만 엔트리 순회가 돌았지만, 지금은 설정 화면을 열거나 기간을 바꿀 때마다 돕니다. 화면을 열 때는 기본 탭과 고급 탭 카운터가 따로 있어 2회입니다.
  • 계산은 캐시 스레드에서 동기로 돌기 때문에, 도는 동안 같은 백엔드의 다른 캐시 작업(페이지 로드의 캐시 읽기/쓰기)은 기다립니다. 단말에서 캐시를 상한 가까이(엔트리 21,317개) 채웠을 때도 "계산 중" 표시는 2~3초였습니다(단말 측정 결과). 그래서 기간별 값을 미리 계산해 두는 방식은 적용하지 않았습니다.
  • 원본 순회 코드에 숨은 버그가 있다면, 이제는 삭제할 때가 아니라 설정 화면을 여는 것만으로도 드러날 수 있습니다.
  • 비용은 기간 안 엔트리 순회 하나이고, 원본 기간 삭제의 순회와 같은 수준입니다. 짧은 기간은 최근 엔트리 몇 개만 보고 끝나며, 전체 기간은 헤더 값 하나만 읽습니다.
  • sparse 부모가 있을 때만 자식 맵 읽기 1회와 자식 조회가 더해집니다.
    • 자식 맵은 최대 65,536비트지만, 비트 검사 반복이라 가볍습니다. 실제 비용은 존재하는 자식 수만큼의 MatchEntry 조회입니다.
    • 자식도 캐시 엔트리라 전체 엔트리 수를 넘을 수 없고, 자식 하나당 조회 비용은 순회에서 엔트리 하나를 꺼내는 비용과 같습니다. 최악이라도 "4주" 계산의 2배 수준입니다.
    • MatchEntry가 부르는 FlushIndex()는 Linux(PC, CCNC)에서 아무 일도 하지 않습니다. posix_bypass_mmap이 Android/Fuchsia에서만 켜져 있어 MappedFile::Flush()가 빈 함수입니다.
    • 부모당 자식 수에 상한을 두거나 나눠 실행하는 방안을 검토했지만 적용하지 않았습니다. 비용이 존재하는 자식 수에 비례하고, PC 캐시 기준 sparse 부모는 6개, 자식은 7개입니다.
  • A안보다 가볍습니다. 파일 stat과 블록 파일 할당 추적이 없습니다.

  • 표시값(논리 크기)과 du 감소량의 차이는 표시값과 실제 디스크 감소량 비교와 같은 이유입니다.

4. 부팅 직후 시계 문제

처음 확인한 단말 캐시에는 2020-09-20 날짜의 엔트리 36개가 rankings 목록 맨 앞(가장 최근 위치)에 있었습니다. 부팅 직후 NTP로 시각이 맞춰지기 전 기본 시각에 기록된 엔트리입니다. 순회가 첫 엔트리에서 바로 멈춰 모든 기간이 0으로 표시됐습니다. 원본 기간 삭제(DoomEntriesBetween)도 같은 이유로 아무것도 지우지 못하므로, 표시값과 실제 삭제는 서로 맞습니다(알려진 한계의 시계 역행과 같은 원인). 측정할 때는 부팅 후 시각 동기화를 기다린 뒤 Video+를 실행해야 합니다.

캐시 상한

CCNC는 --disk-cache-size 옵션과 DiskCacheSize 정책이 없어, 앱이 시작될 때 BackendImpl::AdjustMaxCacheSize()가 남은 공간으로 상한을 정합니다(net/disk_cache/cache_util.cc PreferredCacheSize()).

계산식 (Linux HTTP 캐시)

A = 남은 디스크 공간 + 현재 캐시 크기(index num_bytes). Windows가 아니면 HTTP 캐시는 기본 계산값을 4배로 늘리되, A의 20%를 넘지 않게 자릅니다.

A기본 계산값최종 상한
100 MiB 미만A의 80%A의 80%
100 ~ 400 MiB80 MiB80 MiB
400 ~ 800 MiB80 MiBA의 20% (80~160 MiB)
800 ~ 2,000 MiBA의 10%A의 20% (160~400 MiB)
2,000 ~ 4,000 MiB200 MiBA의 20% (400~800 MiB)

  • 마지막에 index 테이블 크기로 정해지는 상한(MaxStorageSizeForTable = table_len × 240 MB / 64K)과 비교해 더 작은 값을 씁니다. 테이블 크기는 캐시를 처음 만들 때 정해지고 바뀌지 않습니다.
  • 전체 상한 1,280 MiB(1,342,177,280 B, 약 1.34 GB)는 80 MiB × 4 × 4에서 나옵니다. 저장 공간이 아무리 커도 넘지 않습니다.

  • 캐시 크기가 상한 + 80 MiB를 넘은 상태로 열리면 kInvalidCacheSize로 판단되어, kResetOnError로 캐시 전체가 지워지고 새로 만들어집니다(backend_impl.cc, http_cache.cc). PC에서 만든 1.02 GB 캐시를 단말에 넣었을 때 캐시가 7 MB로 초기화된 원인입니다.
  • 상한을 넘으면 eviction이 오래된 엔트리부터 지워 상한보다 약 1 MB 작게 맞춥니다.

알려진 한계

  • 시계 역행: rankings 목록은 넣은 순서라, 시계가 과거로 돌아간 적이 있으면 순회가 일찍 멈춥니다. 표시값과 실제 삭제가 함께 작아지며, 원본 Chromium 기간 삭제와 같은 한계입니다. 단말에서는 부팅 직후 시각 동기화 전(2020년 기본 시각)에 기록된 엔트리 때문에 모든 기간이 0으로 나오는 경우를 확인했습니다(단말 측정 결과 4).
  • 시점 차이: 기간 시작 시각을 계산 시점과 삭제 시점에 각각 정합니다. 그 사이 쌓인 캐시나 사용 중인 엔트리는 결과가 조금 달라질 수 있습니다.
  • 사용 중인 sparse 부모: 계산은 디스크의 자식 맵을 읽습니다. 반면 실제 삭제는 부모가 닫히는 순간의 메모리 맵을 씁니다(~EntryImpl → ~SparseControl이 맵 기록 → DeleteEntryData() → DeleteChildren()). 그래서 부모가 열린 채 재생 중이면, 계산 이후 부모가 닫힐 때까지 새로 받은 자식도 함께 지워져 표시값보다 많이 지워집니다. 계산 시점의 메모리 맵을 읽도록 바꿔도 이후 생기는 자식은 예측할 수 없어, "계산과 삭제 사이에 쌓인 캐시"와 같은 시점 차이 한계로 둡니다.
  • 설정 화면을 여는 시점의 부수 효과: 비정상 종료로 남은 dirty 엔트리를 원본 코드가 그 자리에서 정리합니다. 경로는 두 가지입니다. 순회(GetEnumeratedEntry → InternalDoomEntry)와, sparse 자식 조회(MatchEntry가 해시 체인에서 dirty 엔트리를 만나면 DestroyInvalidEntry)입니다. 원본 기간 삭제와 SyncDoomEntry도 같은 경로를 타므로 결과는 같고, 코드 변경도 아닙니다.
