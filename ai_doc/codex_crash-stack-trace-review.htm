CCOS sig handler를 유지하면서 webappmanager에서도 crash stack trace 받기

크래시 시그널을 DLT에게서 되찾아 백트레이스를 찍고, 원래 주인에게 시그널을 다시 넘겨주는 체이닝 구현에 대한 리뷰입니다. "둘 다 동작 가능한가"라는 질문에 답하기 위해 MOBIS_CCNC와 MOTREX_CCNC의 SIG/DLT 경로를 분리해서 재분석했습니다.

00 플랫폼별 SIG/DLT 경로 분류

두 타깃은 같은 MOBIS_CCNC || MOTREX_CCNC 가드로 묶기에는 signal handler 주인이 다릅니다.

항목 MOBIS_CCNC MOTREX_CCNC
webapp extension의 명시적 crash handler 등록 있음. WebAppExtensionCore::Initialize()에서 port::DebugHandler::getInst()->registryDebugHandler() 호출. 없음. 해당 코드는 #if defined(MOBIS_CCNC)로만 감싸져 있어 MOTREX에서는 컴파일되지 않음.
handler 구현/라이브러리 성격 WebAppDebugHandler → HDebugHandler 계열로 보임. CMake도 mobis-ccnc에서만 htrace를 찾고, sysroot include에 ccos/include/htrace가 포함됨. webappmanager PAL의 WebAppDebugHandler/HDebugHandler 경로가 아님. crash signal을 잡는 주체가 있다면 obigo-logger/libdlt 또는 하위 플랫폼 DLT 경로로 봐야 함.
DLT/log define OBIGO_USE_LOG_SYSTEM은 공통으로 켜질 수 있고, 빌드 옵션에 따라 OBIGO_USE_HYUNDAI_LOG_SYSTEM 또는 OBIGO_USE_DLT_LOG_SYSTEM이 추가됨. 따라서 "DLT로 출력" 경로와 "CCOS crash handler" 경로를 동일한 것으로 보면 안 됨.
현재 패치의 체이닝 대상 의도상 registryDebugHandler()가 설치한 이전 handler. 단, HDebugHandler가 return하는지, 내부에서 re-raise/exit하는지 확인 필요. EnableInProcessStackDumping() 호출 직전 이미 설치되어 있던 handler. 로컬 근거상 webappmanager DebugHandler는 아니며, 대부분의 리스크는 DLT/logging handler와의 상호작용으로 분류해야 함.
리스크 분류 handler semantics 불명. 직접 호출 방식이 sa_mask/SA_RESETHAND를 보존하지 못하는 문제가 더 큼. DLT deadlock/지연 리스크. signal handler 안의 WriteLog()와 platform crash report 순서가 핵심.

근거: src/obigo/web_application_extension_core.cc:31, src/obigo/port/utils/ccnc/trace.cc:26, src/obigo/CMakeLists.txt:238-294, 436-445, src/build/config/obigo.gni:590-619

재분석 결론

MOBIS_CCNC와 MOTREX_CCNC를 같은 이전 handler로 가정하면 안 됩니다. MOBIS는 WebAppDebugHandler/HDebugHandler 쪽을 보존해야 하는 문제이고, MOTREX는 현재 코드상 webappmanager DebugHandler가 없으므로 obigo-logger/libdlt 쪽과의 충돌 문제로 봐야 합니다.

따라서 공통 코드는 유지하더라도 진단/체이닝 정책은 플랫폼별로 나누는 게 안전합니다. 특히 ChainToPreviousHandler() 앞뒤 순서와 WriteLog() 사용 여부는 MOBIS와 MOTREX에서 같은 결론이 아닐 수 있습니다.

01 결론

체이닝 방식 자체는 필요합니다. 다만 "무엇을 체이닝하는지"가 MOBIS와 MOTREX에서 다릅니다.

플랫폼별 조건부 가능

MOTREX 계열에서 확인한 libdlt 경로는 sigaction()의 oldact 인자에 NULL을 넘깁니다. 즉 이전 핸들러를 저장하지도 체이닝하지도 않습니다. 구조가 "나중에 설치한 쪽이 무조건 이긴다"라면, 나중에 설치하는 쪽이 이전 핸들러를 명시적으로 보존/호출해야 webappmanager stack trace와 플랫폼 crash report를 같이 얻을 수 있습니다.

반면 MOBIS는 WebAppDebugHandler/HDebugHandler 경로가 따로 있으므로 libdlt와 같은 return/re-raise semantics라고 단정하면 안 됩니다. MOBIS에서는 실제 이전 handler 심볼과 return 여부를 먼저 찍어야 "둘 다 동작"을 말할 수 있습니다.

MOTREX/libdlt 경로에서 역어셈블로 확인한 사실

oldact=NULL 판단 근거

libdlt 소스가 아니라 MOTREX sysroot의 실제 바이너리 libdlt.so.2.17.0을 역어셈블해서 판단했습니다. AArch64 호출 규약에서 sigaction(signum, act, oldact)의 세 번째 인자 oldact는 x2 레지스터로 전달됩니다. 아래 호출부들은 sigaction@plt 직전에 모두 mov x2, #0x0을 수행하므로 oldact == NULL입니다.

성립 조건
  • EnableInProcessStackDumping()이 해당 플랫폼의 crash handler 등록보다 반드시 나중에 호출될 것
  • 그 사이에 아무도 다시 뺏어가지 않을 것
  • MOTREX/libdlt는 return semantics가 확인됐지만, MOBIS/HDebugHandler는 별도 확인할 것
  • 백트레이스 출력 도중 행/데드락이 안 날 것 — 현재 크래시 테스트에서는 정상 출력 확인됨. 단, DLT lock 보유 중 crash 같은 재진입 케이스는 별도 리스크로 남음 (#3, #4)

01 Blocker

검증용으로 켠 config가 이 빌드에서 쓰이지 않는 파일입니다

args.gn은 motrex_ccnc = true이고 mobis_ccnc는 없습니다. 빌드 스크립트의 brs_build_install_config()는 motrex-ccnc에 대해 configuration/motrex-ccnc/만 복사합니다(release 분기도 없음).

02 Blocker

이 빌드에서는 CCOS DebugHandler가 아예 등록되지 않습니다

// src/obigo/web_application_extension_core.cc:31
#if defined(MOBIS_CCNC)          // ← MOTREX_CCNC 없음
  port::DebugHandler::getInst()->registryDebugHandler();
#endif

추가로 SDK sysroot를 전수 스캔한 결과:

  • dlt_signal_handler_registration을 undefined로 참조하는 .so가 sysroot 전체에 하나도 없음
  • libwebappmanager-plugin-pal.so.3.0.0에 WebAppDebugHandler / HDebugHandler 심볼 없음
  • libobigo_logger.a는 WebAppLog::{registerContext, unregisterContext, printLog}만 참조 (시그널 관련 없음)

MOTREX 타깃에서 "CCOS DebugHandler가 crash sig event를 가져간다"는 전제는 성립하지 않습니다. 적어도 이 코드베이스 기준으로 MOTREX에서는 WebAppDebugHandler/HDebugHandler 등록 코드가 빠져 있습니다. 이전 handler가 잡힌다면 그 주체는 webappmanager DebugHandler가 아니라 obigo-logger/libdlt 또는 하위 플랫폼 DLT 경로로 분류해야 합니다.

체이닝 코드 자체는 이전 핸들러가 없으면 no-op이므로 해가 되지는 않습니다. 다만 MOBIS와 MOTREX가 서로 다른 SIG/DLT library를 쓰는 구조이므로, 무엇을 상대로 체이닝하는지 모른 채 공통 정책을 적용하는 건 리스크입니다.

조치08장의 진단 로그로 각 프로세스에서 실제 이전 핸들러가 무엇인지 먼저 확정. 로그에는 플랫폼명, signal 번호, 이전 handler 심볼, so 이름을 함께 남겨 MOBIS/HDebugHandler와 MOTREX/libdlt를 분리해 판단

04 심각 — 기존 동작 후퇴

03 Major

체이닝 순서 때문에 플랫폼 크래시 리포트가 뒤로 밀립니다

기존에는 크래시 즉시 첫 동작이 플랫폼 리포트 전송이었습니다. 지금은 수십 번의 DLT 왕복이 끝나야 리포트가 나갑니다. 현재 테스트에서는 크래시 코드와 백트레이스가 잘 출력되는 것을 확인했습니다. 따라서 이 항목은 즉시 재현되는 장애라기보다, DLT 지연/락 경합/워치독 개입 시 플랫폼 리포트가 뒤로 밀릴 수 있는 구조적 리스크입니다.

다만 이 구간을 지켜줄 alarm(5) 워치독은 한참 뒤에서야 설정됩니다. 정상 크래시 테스트는 통과했지만, 백트레이스 중 행이 나는 재진입 케이스까지 커버하지는 못합니다.

조치 최소 — alarm() + SIGALRM 핸들러 설치를 in_signal_handler = 1; 직후로 앞당깁니다. 무슨 일이 있어도 5초 안에 exit_group 보장.
MOTREX 권장 — ChainToPreviousHandler()를 StackTrace().Print() 앞으로 이동. 확인된 dlt_sig_handler는 return 하므로 백트레이스는 그대로 찍힙니다.
MOBIS 보류 — HDebugHandler가 return 하는지 미확인이므로 같은 순서 변경을 바로 적용하지 말고, 실제 심볼/동작 확인 뒤 별도 정책으로 결정해야 합니다.
src/base/debug/stack_trace_posix.cc:565-576, 647-654
04 Major

시그널 핸들러 안의 WriteLog() — 재진입 리스크

WriteLog → ImplHLogDelegate::WriteLog → WebAppLog::printLog(std::shared_ptr<DltContext>, ...). 시그니처상 shared_ptr 복사(refcount) + 내부 DLT 세마포어가 들어갑니다. 일반 크래시 테스트에서는 크래시 코드와 백트레이스가 정상 출력되었습니다. 다만 크래시가 로깅 경로 안에서(또는 DLT 락 보유 중) 발생하면 같은 스레드가 자기 락을 기다리는 재진입 리스크가 남습니다.

EnableInProcessStackDumping()의 워밍업은 컨텍스트 지연 등록만 막습니다. 호출당 락/할당은 못 막습니다. 주석에도 "not async-signal safe"라고 인정하고 있으니 남는 건 완화책입니다.

기존 코드가 핸들러 맨 앞에서 FinalizeLogger()를 부르던 게 정확히 이 위험 회피였을 수 있다는 점도 고려해 주세요. (git 이력상 92→143 병합 때 들어온 코드라 의도는 불분명합니다.)

조치현재 테스트 결과상 필수 블로커는 아닙니다. 안정성을 더 올리려면 #3의 alarm() 선행 이동을 안전장치로 두고, 장기적으로는 기동 시 미리 열어둔 fd에 write()만 하는 fallback 경로를 검토합니다.
src/base/debug/stack_trace_posix.cc:1121-1125
05 Major

MirrorToDlt가 스위치와 무관하게 항상 동작합니다

PrintToStderr()의 가드는 OBIGO_USE_LOG_SYSTEM && ARCH_CPU_ARM64뿐이고 kEnableCrashStackTrace와 무관합니다. 따라서 스위치가 off여도 DCHECK 실패, DumpWithoutCrashing(), 각종 StackTrace().Print() 출력이 전부 DLT로 나갑니다. 로그 폭주 + 성능 영향.

여기에 더해 is_official_build = false라서 content_main_runner_impl.cc:996-999가 이미 모든 프로세스에서 EnableInProcessStackDumping()을 호출하고 있습니다. 즉 이 스위치가 실제로 제어하는 건 "스택 덤프 활성화"가 아니라 "DLT에게서 시그널을 되찾아오기"입니다. 스위치 이름·주석과 실제 의미가 어긋납니다.

조치전역 bool g_mirror_to_dlt = false;를 두고 EnableInProcessStackDumping()에서 스위치 값으로 세팅, MirrorToDlt() 진입부에서 early return. config 설명도 실제 의미로 수정.
src/base/debug/stack_trace_posix.cc:399-407 · src/content/app/content_main_runner_impl.cc:996-999

05 중간

06Medium

FinalizeLogger() 위치 때문에 [end of stack trace]가 DLT에 안 남습니다

StackTrace().Print()  →  FlushDltLine()  →  Chain  →  FinalizeLogger()
   →  (x86 전용 레지스터 덤프, ARM64에선 skip)
   →  PrintToStderr("[end of stack trace]\n")   ← WriteLog는 이미 early return

종료 마커가 DLT에 없으면 로그가 잘린 건지 정상 종료한 건지 구분이 안 됩니다. 크래시 로그에서 가장 중요한 정보입니다. 또한 체인된 핸들러가 return 하지 않는 구현이면 FinalizeLogger() 자체가 실행되지 않습니다.

조치FinalizeLogger()를 "[end of stack trace]" 출력 + FlushDltLine() 뒤, re-raise 직전으로 이동
07Medium

g_dlt_line 전역 버퍼에 동기화가 없습니다

PrintToStderr()는 시그널 컨텍스트 밖에서도 쓰입니다(임의 스레드의 StackTrace().Print()). g_dlt_line / g_dlt_line_len에 락이 없어서 두 스레드 출력이 한 줄로 섞이고, 크래시 첫 줄의 [WMP][##CRASH##] 프리픽스가 누락될 수 있습니다.

경계는 확인해 봤고 오버플로는 나지 않습니다 (FlushDltLine의 g_dlt_line[511]='\0'까지 안전). 다만 프리픽스 복사 루프에는 경계 검사가 아예 없습니다 — 지금은 17바이트라 안전하지만 kDltCrashPrefix가 길어지면 바로 깨집니다.

512바이트 라인 잘림

07 크래시 없이 검증하는 방법

"CCOS sig handler가 잘 동작 중인지 테스트 불가"가 가장 큰 리스크인데, 아래 두 가지로 크래시를 일으키지 않고 판별 가능합니다. 둘 다 시그널 컨텍스트 밖이라 async-signal safety 제약이 없습니다.

A. 무엇을 뺏어왔는지 확인

EnableInProcessStackDumping()의 캡처 루프 안에서:

Dl_info dli;
const void* prev = (previous.sa_flags & SA_SIGINFO)
    ? reinterpret_cast<void*>(previous.sa_sigaction)
    : reinterpret_cast<void*>(previous.sa_handler);
LOG(ERROR) << "[RLOG] sig=" << crash_signal << " prev=" << prev
           << " name=" << (prev && dladdr(prev, &dli) && dli.dli_sname
                           ? dli.dli_sname : "(none/SIG_DFL)");

프로세스마다 다르게 나오므로 browser / renderer / gpu / utility 4개 모두 확인

dlt_sig_handler가 찍히면 전제 확인 완료, (none/SIG_DFL)이면 애초에 아무도 안 잡고 있었다는 뜻입니다.

B. 나중에 다시 뺏기는지 확인

기동 후 10초 / 60초 타이머에서:

struct sigaction cur = {};
sigaction(SIGSEGV, nullptr, &cur);
LOG(ERROR) << "[RLOG] SIGSEGV owner still ours? "
           << (cur.sa_sigaction == &StackDumpSignalHandler);

CCOS/PAL이 lazy하게 나중에 등록하는 구조라면 false가 찍히고, 그 경우 EnableInProcessStackDumping() 호출 지점을 더 뒤로 옮겨야 한다는 결론이 바로 나옵니다.

A / B를 붙이면 지금의 [RLOG] 4줄(스위치 값 확인)보다 훨씬 답에 가까운 정보를 얻습니다.
