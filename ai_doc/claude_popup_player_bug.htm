백그라운드 재생 중인데 홈에서 팝업 플레이어가 뜨지 않는다

TikTok 라이브를 재생하고 홈으로 돌아오면 재생은 계속되는데 팝업 플레이어가 표시되지 않습니다. SE10 헤드유닛에서만 발생하고 삼성 태블릿에서는 정상이었습니다. 두 단말의 계측 로그를 비교해 원인을 사이트 설정의 User-Agent 한 줄까지 좁혔습니다.

01 증상

기능의 목적과 실제 동작이 어긋나는 지점.

팝업 플레이어는 백그라운드 탭에서 미디어가 재생 중일 때 홈 화면에 재생 정보를 띄워주는 기능입니다. 사용자가 다른 탭에서 영상을 틀어두고 홈으로 돌아와도 무엇이 재생 중인지 알 수 있게 합니다.

SE10에서는 TikTok 라이브가 실제로 재생되고 있는데도 홈에서 팝업이 뜨지 않았습니다. 같은 시나리오를 삼성 태블릿에서 돌리면 정상적으로 표시됩니다.

04 원인 사슬

설정에서 시작해 렌더러와 코어를 거쳐 팝업 플레이어까지 이어지는 6단계. 각 단계가 일어나는 계층을 태그로 표시했습니다.

1
설정
SE10의 TikTok 사이트 설정이 Windows 데스크톱 User-Agent를 강제합니다. 삼성은 null(오버라이드 없음)입니다. PickNow 서버 사이트 설정 · userAgent
2
사이트
TikTok이 데스크톱 웹앱 번들을 내려줍니다. webapp-desktop 리소스가 SE10에서 46회, 삼성에서 0회 로드됐습니다. https://www.tiktok.com/webapp-desktop/static/worker/vodsr-worker-*.js
3
사이트
데스크톱 라이브 플레이어는 저지연을 위해 WebRTC / MediaStream으로 재생합니다. 표준적인 구현이며 규격 위반이 아닙니다.
4
렌더러
미디어 소스가 MediaStream이므로 Blink가 WebMediaPlayerImpl 대신 WebMediaPlayerMS를 생성합니다. 이 재생기는 스트림 길이·성격과 무관하게 조건 없이 MediaContentType::kOneShot을 보고합니다. content/renderer/media/media_factory.cc:363 · web_media_player_ms.cc:599
5
코어
AddPlayer()가 kOneShot을 AddOneShotPlayer()로 라우팅 → one_shot_players_에만 들어가 HasOnlyOneShotPlayers()가 참이 됩니다. 그 결과 IsControllable()이 즉시 false를 반환하는데, playback_state는 kPlaying으로 남습니다. content/browser/media/session/media_session_impl.cc:788 · 1113
6
오비고
OBAPopupPlayer가 isControllable=false를 그대로 받아 mIsControllable을 내립니다. 이어서 Chromium이 2.5초 뒤 거는 지연 hide가 재생 중인데도 팝업을 내리고 상태를 리셋합니다. 홈 복귀 시 show()가 막힙니다. OBAPopupPlayer.mediaSessionStateChanged() · hidePlayController()

핵심 모순 — IsControllable()과 playback_state가 서로 다른 기준을 씁니다. 전자는 HasOnlyOneShotPlayers()에서 단락되고, 후자는 오디오 포커스 상태만 봅니다. 그래서 “재생 중인데 controllable=false” 라는 조합이 만들어집니다.

kOneShot은 media/base/media_content_type.h에 “제어할 수 없는 플레이어”로 정의되어 있습니다 (“Type indicating that a player cannot be controlled.”). 그 분류가 붙는 순간 IsControllable()이 false를 반환하는 건 설계대로입니다. 결함은 판정 로직이 아니라, 몇 시간짜리 라이브 방송에까지 그 분류를 붙이는 WebMediaPlayerMS의 분류 한 곳입니다.

MediaStream을 “제어 불가”로 싸잡는 분류

WebMediaPlayerMS가 스트림 길이·성격을 보지 않고 kOneShot을 보고합니다. IsControllable()의 단락은 그 분류에 충실한 정상 동작이므로, 결함은 분류 한 곳입니다.

오비고 코드

isControllable은 “OS 미디어 컨트롤을 붙일 자격이 있는가”입니다. 팝업 플레이어가 알아야 할 것은 “재생 중인가”이고, 그 값은 같은 이벤트의 isPaused에 있었습니다.

09 수정

Chromium 원본 파일은 건드리지 않고 OBAPopupPlayer.java 한 파일 61줄만 변경. 4번은 아래 사이드 이펙트 완화입니다.

#위치내용
1 mediaSessionStateChanged() 재생 중(!isPaused)이고 직전이 controllable이었다면 isControllable=false를 무시
2 hidePlayController() 재생 중이면 2.5초 지연 hide를 무시 — 상태 리셋을 막음
3 show() 대상 탭이 닫혔으면 표시하지 않고 상태 정리 — 2번이 만드는 “재생 중 탭 종료” 케이스 대응
4 mIsTransportEnabled 표시 가능 여부와 전송 제어 가능 여부를 분리 — 동작하지 않는 버튼이 활성으로 보이지 않게

1번의 “직전이 controllable이었을 때만”이 핵심입니다. AddOneShotPlayer()는 항상 (controllable=1) → (controllable=0) 순서로 통지하므로 WebRTC 라이브는 걸리고, 처음부터 controllable이 아닌 짧은 효과음(kTransient, 5초 이하)에는 팝업이 뜨지 않습니다.

10 수정의 사이드 이펙트

값이 바뀌는 소비처를 전수 추적한 결과. 하나는 완화 조치를 함께 적용했습니다.

버튼 무반응은 기존 버그이지만, 드러낸 것은 우리 수정입니다.

one-shot 플레이어는 OnSuspendInternal()이 HasOnlyOneShotPlayers()에서 즉시 반환하므로 원래부터 suspend/resume이 먹지 않습니다. 이건 Chromium 원본 동작입니다. 다만 수정 전에는 팝업 자체가 뜨지 않아 사용자가 그 버튼에 닿을 수 없었습니다. 수정으로 팝업이 뜨면서 이미 존재하던 한계가 사용자에게 노출된 것입니다. 참고로 OS 미디어 알림 경로에서는 지금도 (controllable=1)인 1ms 동안 알림이 떴다가 2.5초 뒤 사라지므로, 그 사이 같은 무반응이 이미 존재합니다.

심각도항목내용조치
HIGH 재생/일시정지 버튼 무반응 기존 Chromium 한계가 노출됨. resume()은 재생 없이 오디오 포커스만 탈취 완화 적용
MID 사용시간 통계 변화 isPlaying()이 true가 되어 TabImpl.hide()·ChromeActivity.onStop()의 sendUsageTime이 전송되지 않고 누적 정책 판단 필요
MID 정지된 팝업 잔존 렌더러 크래시·OOM 탭 폐기 시. 홈에 머무는 동안 재평가 트리거 없음 show()에서 부분 정리
LOW 홈 배너 레이아웃 isPopupPlayerVisible()로 홈 웹앱이 배너를 조정. 팝업이 늘면 배너가 숨는 경우도 늘어남 의도된 변화 · 공유
LOW 기존 정상 사이트 삼성 로그 전이 17건 전수 확인 결과 분기 진입 0회. kPersistent 경로는 이 코드를 지나가지 않음 영향 없음
LOW 짧은 효과음 && mIsControllable 가드가 kTransient를 걸러냄 영향 없음

완화 — 표시와 제어의 분리

“팝업을 띄울 수 있는가”와 “버튼이 실제로 먹는가”를 다른 값으로 관리합니다.

// 표시용 — 재생 중이면 유지된다
private boolean mIsControllable = false;
// 제어용 — 코어가 준 원본 값을 그대로 쓴다
private boolean mIsTransportEnabled = false;

// mediaSessionStateChanged()
mIsTransportEnabled = isControllable;              // 보정 전 원본
if (!isControllable && !isPaused && mIsControllable) {
    effectiveControllable = true;
    disabledButton();                          // 표시는 유지, 전송 제어는 차단
}

// updatePlayController() — 다음 갱신이 버튼을 다시 켜지 않도록
playPauseBtn.setEnabled(mIsTransportEnabled);      // 기존: setEnabled(true)
동작완화 전완화 후
팝업 표시 · 제목 · 앨범아트정상정상
재생/일시정지 버튼활성인데 무반응비활성 (눌리지 않음)
재생 버튼의 오디오 포커스 탈취발생차단
팝업 탭 → 탭 전환동작동작
닫기(X) 버튼동작동작

일반 사이트는 mIsTransportEnabled == isControllable == true 이므로 이전과 완전히 동일하게 동작한다.

11 남은 과제

갱신 정지

is_controllable=0이 되면 Chromium이 mNotificationInfoBuilder를 null로 만들어 이후 updatePlayController가 오지 않습니다. 초기 표시는 정상이지만 방송 전환 시 제목·아트워크 갱신이 안 될 수 있습니다. 해결하려면 MediaSessionHelper.java(원본)를 수정해야 해서 이번 범위에서 제외했습니다.

UA 설정

서버 설정에서 SE10의 userAgent 오버라이드를 제거하면 이번 케이스 자체가 사라집니다. 코드 수정과 배타적이지 않습니다. 코드 수정은 다른 사이트가 WebRTC 라이브를 쓸 때도 동작하게 하므로 둘 다 적용을 권합니다.

업스트림 제기

WebMediaPlayerMS의 kOneShot 하드코딩은 Chromium 버그로 별도 제기할 사안입니다. 제품 일정과 분리해 진행하는 것이 맞습니다.
