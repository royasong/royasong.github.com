크래시 덤프(.dmp)로 크래시 위치 찾는 방법

단말에서 chrome_crashpad_handler가 만든 minidump(<UUID>.dmp)을 받아서, 어느 코드에서 죽었는지(심볼화된 콜스택)를 뽑아내는 절차.

목차
  1. 전제
  2. 단말에서 .dmp 받아오기
  3. 분석 툴(minidump_stackwalk, dump_syms) 준비 — 호스트 x64용
  4. 심볼(.sym) 생성
  5. minidump_stackwalk 실행
  6. 결과 읽기
  7. 트러블슈팅

0.전제

크래시 시 단말의 아래 경로에 <UUID>.dmp / <UUID>.meta 파일 쌍이 자동 생성됨 (crashpad 자체 기능, is_official_build 값이나 이 저장소의 다른 수정사항과 무관하게 항상 생성됨):

/ccOSData/web/AGBAsset/.config/chromium/Crash Reports/pending/
scp -r /ccOSData/web/AGBAsset/.config/chromium/Crash\ Reports/pending/* obigo@192.168.105.36:/home/obigo/aa__target/

분석에 필요한 것 2가지:

  1. 호스트(x86_64)용 minidump_stackwalk / dump_syms 실행 파일
  2. 크래시 난 시점의 motrex_143 unstripped webappmanager 바이너리 (심볼 추출용, BuildID가 정확히 일치해야 함)

1.단말에서 .dmp 받아오기

경로에 공백(Crash Reports)이 있어서 scp가 자주 깨진다. ssh ... cat으로 받는 게 안전하다.

ssh root@<단말IP> "cat '/ccOSData/web/AGBAsset/.config/chromium/Crash Reports/pending/<UUID>.dmp'" \
  > ./<UUID>.dmp

2.분석 툴(minidump_stackwalk, dump_syms) 준비 — 호스트 x64용

⚠️ motrex_143(out_motrex-ccnc/Release)에서는 빌드하지 말 것. 이 out 디렉토리는 ARM64 크로스컴파일용이라, 기본 타깃으로 빌드하면 ARM64 바이너리가 나와서 이 PC에서 실행이 안 된다(Exec format error). GN의 세컨더리(host) 툴체인을 통해 빌드하려는 시도도 해봤지만, 실제로 이 그래프엔 그 툴체인으로 가는 진짜 ninja 빌드 엣지가 없어서 unknown target 에러만 난다(막다른 길).

대신 /home/obigo/server/143origin/obigo-af-agb-143(같은 chromium 143, target_cpu="x64"로 gn gen된 네이티브 x64 빌드)에서 빌드한다. breakpad 툴 자체는 OBIGO 커스터마이징과 무관한 순정 코드라 이걸 그대로 써도 된다.

cd /home/obigo/server/143origin/obigo-af-agb-143
./build.sh    # chrome 빌드 + minidump_stackwalk/dump_syms까지 같이 빌드하도록 되어 있음

결과물:

/home/obigo/server/143origin/obigo-af-agb-143/src/out/Debug/minidump_stackwalk
/home/obigo/server/143origin/obigo-af-agb-143/src/out/Debug/dump_syms

(file로 확인해서 x86-64인지 꼭 확인. aarch64가 나오면 잘못 빌드된 것)

3.심볼(.sym) 생성

크래시가 난 바로 그 시점의 motrex_143 webappmanager(unstripped, out_motrex-ccnc/Release/webappmanager)로 생성한다. 코드를 다시 빌드해서 바이너리가 바뀌면 BuildID도 바뀌므로, 바이너리를 재빌드했다면 이 단계도 다시 해야 한다.

DUMP_SYMS=/home/obigo/server/143origin/obigo-af-agb-143/src/out/Debug/dump_syms
cd /home/obigo/work/motrex_143/linux-af/oaf/brs_143/src
"$DUMP_SYMS" out_motrex-ccnc/Release/webappmanager > webappmanager.sym

첫 줄에 모듈명/디버그ID가 찍힌다:

head -1 webappmanager.sym
MODULE Linux arm64 <DEBUG_ID> webappmanager

이 <DEBUG_ID>로 breakpad가 요구하는 심볼 디렉토리 구조를 만든다 (경로가 전부 상대경로이므로, 위에서 webappmanager.sym을 만든 디렉토리에서 이어서 실행):

cd /home/obigo/work/motrex_143/linux-af/oaf/brs_143/src
SYMDIR=./symbols/webappmanager/<DEBUG_ID>
mkdir -p "$SYMDIR"
cp webappmanager.sym "$SYMDIR/webappmanager.sym"

(<DEBUG_ID>는 .sym 첫 줄에 찍힌 값을 그대로 복사 — 사람이 손으로 재계산하지 말 것)

4.minidump_stackwalk 실행

⚠️ 주의 이 버전의 CLI는 일반적으로 알려진 breakpad 문법과 다르다. -s는 "심볼 경로" 플래그가 아니라 "스택 내용 출력" 불리언 옵션이다. 심볼 경로는 위치 인자로, minidump 파일 뒤에 온다. 
MDSW=/home/obigo/server/143origin/obigo-af-agb-143/src/out/Debug/minidump_stackwalk
"$MDSW" ./<UUID>.dmp ./symbols > stackwalk_result.txt

5.결과 읽기

출력 맨 위에 크래시 원인/주소, 이어서 각 스레드의 콜스택이 나온다. Thread N (crashed)로 표시된 스레드가 실제로 죽은 스레드다.

Crash reason:  SIGBUS / BUS_ADRALN
Crash address: 0xffffffffff

Thread 0 (crashed)
 0  0xffffffffff
     pc = 0x000000ffffffffff
 1  webappmanager!content::WebContentsImpl::WebContentsImpl(content::BrowserContext*) + 0x73c
 2  webappmanager!(anonymous namespace)::CreateTargetContents(...) + 0x294
 3  webappmanager!Navigate(NavigateParams*) + 0xdd8
 4  webappmanager!StartupBrowserCreatorImpl::OpenTabsInBrowser(...) + 0x6ac

0 0xffffffffff 같은 최상단 프레임은 크래시가 난 그 지점(PC)이고, 그 아래(1, 2, ...)가 그걸 호출한 콜스택 — 즉 프레임 1이 실제로 문제를 일으킨 코드 위치인 경우가 많다(위 예시는 WebContentsImpl 생성자 안에서 잘못된 함수 포인터를 호출한 테스트 케이스).

6.트러블슈팅

ERROR: MinidumpThread cannot read context 등으로 아예 안 읽힘
잘못된(너무 오래되었거나 아키텍처가 다른) minidump_stackwalk를 쓴 것. 반드시 같은 chromium 버전(143) 소스에서 빌드한 걸 써야 한다.
콜스택에 심볼 없이 주소만 나옴 (webappmanager!??? 등)
.sym의 <DEBUG_ID>가 실제 크래시 당시 바이너리와 다름 (재빌드 후 심볼 재생성 안 함) — 2~3단계를 다시.
ninja: error: unknown target '...(...)'​
GN 라벨 문법(target(//toolchain:label))을 그대로 ninja/autoninja 커맨드라인에 넣은 것. 그건 gn ls/gn desc 전용 문법이라 ninja는 이해 못 한다. 2단계처럼 애초에 네이티브 x64로 gn gen된 트리(obigo-af-agb-143)를 쓰는 걸 추천.
